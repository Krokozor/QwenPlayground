# Архитектура QwenPlayground

Карта для долгосрочной разработки: из чего состоит проект, как связаны модули, кто чем
владеет и какие инварианты держат дом. Правила поведения агента — в `main-agent.md`,
история решений — в `refactoring.md`. Этот документ — про устройство дома.

## Общая картина

WPF-приложение (MVVM-лайт) вокруг локальной llama.cpp-модели. Резидентный агент
(main-agent) живёт в постоянной сессии и развивает приложение сам через rebuild_self.
Два слоя:

- **`src/QwenPlayground.Core`** — домен без UI: агентный цикл, шаблон/парсер Qwen,
  инструменты, память, компакция, настройки, самосборка. Тестируется (Core.Tests).
- **`src/QwenPlayground.App`** — WPF-оболочка: ViewModel'и, окна, UI-инструменты,
  композиция сервисов. Тестируются чистые части (App.Tests).

Плюс `tools/QwenPlayground.Harness` — консольные сценарии против живого сервера;
`run/<id>/` — развёрнутые версии приложения (pointer-layout), `assets/chat_template.jinja`
— эталон шаблона Qwen.

## Модель потоков (главный инвариант)

**Весь агентный код исполняется на потоке UI**: цикл генерации, инструменты, компакция,
heartbeat, flush памяти сериализуются диспетчером. Фоновые потоки допустимы только для
I/O с возвратом через `await`. Следствия:

- shared-состояние корректно без локов; блокировки не добавлять;
- тяжёлые вычисления в Core будут фризить UI — уводить через Task.Run + await;
- параллельные ходы (будущий оркестратор) потребуют пересмотра этого пункта.

## Жизненный цикл приложения

`AppLifecycle` (App) — реестр сервисов с Start/Shutdown (`IAppService`); остановка LIFO,
каждый в своём try/catch, ошибки — в статус. Зарегистрированы: heartbeat-таймер,
синхронный flush настроек. MainWindow: `SaveCurrent()` → `vm.Shutdown()`. Новые сервисы
с состоянием (таймеры, подписки, кэши) регистрируются здесь, а не гасятся вручную.

## Источники завершений

`ICompletionSource` (Core/Inference) — контракт над llama.cpp-клиентом: Stream/Complete/
CountTokens + LastUsage. Потребители (PromptPipeline, ServiceCompletionClient, AgentLoop)
принимают фабрику `Func<string, ICompletionSource>` и создают источник под живой эндпоинт.
Это шов мульти-бэкенда и тестовых заглушек (см. PromptPipelineTests); оркестратор сможет
гонять дочерних агентов на других моделях без изменения цикла.

## Владение состоянием

| Состояние | Владелец | Кто мутирует |
|---|---|---|
| Разговор (`ChatLog`) | MainViewModel (экран) | VM, AgentLoop, ContextMaintenance — только через методы лога |
| ID сообщений (счётчик) | ChatLog | лог сам; персистится в SessionData.NextMessageId |
| FSM чата (`ChatStateMachine`) | MainViewModel | цикл (Generating/Awaiting*), maintenance (Compacting) |
| Вид сообщений (`Messages`) | MainViewModel | VM; структурные изменения лога → RebuildMessageViews |
| Настройки (`SettingsStore<AppSettings>`) | синглтон на процесс | тонкие свойства VM пишут напрямую |
| Сессии (sessions/, ChatSessions) | MainViewModel | ChatSessions; бэкапы — ContextBackupStore |
| Серверные факты (`ServerProps`) | MainViewModel | PromptPipeline (n_ctx, media_marker, LastPromptTokens) |
| Память (memories/, layers.json) | файлы | MemoryStore/LayerStore; surfacer только читает |

## Жизненный цикл хода

```
SendAsync / heartbeat / wake / resume
  └─ GenerateWithBudgetAsync
       ├─ EnsureBudget (ContextMaintenance): /tokenize следующего промпта
       │    vs окно − резерв → не влезает или запрошено ⇒ компакция
       └─ GenerateCoreAsync  [FSM Idle→Generating]
            └─ AgentLoop.RunAsync(request)   ← IAsyncEnumerable<AgentEvent>
                 рендер промпта: история + InjectedIdentity (identity+layers+trajectory)
                 + tool-определения + state-блок + мультимодальность
                 стрим токенов → MessageViewModel.AppendStreamChunk (троттлинг ~50 мс)
                 tool_call → ToolRegistry.ExecuteDetailedAsync (+FinalizeAsync)
                 budget-guard между итерациями → EnsureBudget → [Compacting]
            switch по AgentEvent в VM: мутации Messages/_log/StatusText
       SaveCurrent() — персистенция после хода
```

Сборка «следующего промпта» 1-в-1 повторяется в PromptPipeline (превью + пред-отправочный
подсчёт) — единственный источник расхождений, если менять рендер, менять оба места
(тест связки: StateBlockBuilderTests + QwenChatTemplateTests).

## Компакция (ContextMaintenance)

Бэкап сессии (без него не сжимаем) → ветка: суммаризация ранней части через submit_result;
main: слоистый конвейер L1/L2/L3 (MemoryLayerPipeline) → извлечение фактов в memories/
(best-effort). FSM: авто-вызов приходит в Generating и возвращается туда; ручной из Idle —
Idle→Compacting→Idle; запрос во время Generating ставится флагом и исполняется гардом.

## Инструменты

`ToolRegistry` = имя → ToolEntry (определение + исполнитель). Источники — `IToolProvider`:
- `ReflectionToolProvider(Assembly[])` — встроенные [Tool]-классы (Core + App сборки);
- динамическая регистрация `Register(entry)` — точка для MCP-клиента и плагинов.

Интерактив инструментов (ask_user, подтверждение shell) — pull через статический
`AgentInteraction`; оконную реализацию регистрирует `ChatInteraction` при старте.

## Память агента

- **memories/** — долговременные факты (MemoryStore, JSON на факт); классификация
  (категория/вайб/эмбеддинг) — пробами на компаньон-модели, лениво (flush на heartbeat).
- **layers.json** — слои L1 (слитые резюме) / L2 (старый L3) / L3 (свежий) — MemoryLayerStore.
- **live-recall** — MemorySurfacer подтягивает факты во время хода и между итерациями,
  всплывшее попадает в state-блок; наг менеджмента — периодическое напоминание модели.
- **trajectory.md** — «северная звезда» направления, инжектится в системный промпт.
- **diary.md** — человекочитаемый эпизод за компакцию.

Решение владельца (2026-08-25): память **общая по дизайну** — один пул воспоминаний на
процесс, полезных основному агенту; у него одного сложная схема (слои L1-L3). Скрытые
статические чтения настроек в Core/Memory — не долг, а легализация этого решения.
Возможное будущее развитие — фильтрация реколла по активному проекту/папке (сейчас агент
работает только над собой; смысл ограничивать появится, когда работа пойдёт по нескольким
местам). Не скоупить хранилища — только фильтровать выдачу.

## Самосборка (rebuild_self)

`SelfBuildService`: dotnet build/test → копия в run/<id>/ → current.txt pointer → рестарт
через handshake. Внешним разработчикам (opencode и т.п.) собирать в bin/ — безопасно:
работающий экземпляр живёт из run/. Journal (run/journal.json) — источник «последней
сборки» для state-блока и заголовка.

## Настройки

`AppSettings.Get()` — типизированный синглтон (паттерн NekoBot SettingsStore<T>),
файл settings.json, атомарная запись. Свойства VM — тонкие виды: чтение напрямую,
запись = мутация + INPC + дебаунс 800 мс. Новый параметр = поле AppSettings (+вид в VM).

Решение владельца (2026-08-25): плоский формат сохраняем — приложение не микросервисное,
резать на секции рано. Когда появится реальная зона со своими настройками (как «сервис
дискорда» у NekoBot) — заводится отдельный класс с `[SettingsFile("…")]`: `SettingsStore<T>`
дженерик, второй файл подключается без единой правки механизма. Профиль агента для
будущего `spawn()` собирается аддитивно, без переезда полей.

## Цели взаимодействия (типы чата)

Общение с моделью — всегда ради **цели**, и цель первична по отношению к «чату»
(урок NekoBot: ChatType). Сегодня в проекте шесть целей; три из них ещё не названы:

| Цель | Где живёт | Промпты |
|---|---|---|
| main-агент | сессия main, полный цикл (identity+слои+память+tools) | InjectedIdentity + state-блок |
| обычный чат | любая не-main сессия (`SessionData.Purpose="chat"`) | без инъекции |
| резюме ветки | ContextMaintenance | каталог: SummarizationSystem/User |
| слои L1/L2/L3 | MemoryLayerPipeline | каталог: Merge*, Segment* |
| извлечение фактов | ContextMaintenance | каталог: MemoryExtraction + **MemoryExtractionSystem** |

Все сервисные промпты — в `PromptCatalog` (config/prompts.json), правятся во вкладке
«Суммаризация»; ни одной константы промпта в коде быть не должно. `SessionData.Purpose`
делает файлы сессий самоописываемыми. При оркестраторе цели станут профилями
(system-ключ + потолок токенов + контракт результата + tools-флаг) и появлением
`spawn(цель)` для дочерних агентов; SummarizationViewModel превратится в универсальное
стекло по всем целям.

**Фундамент профилей сделан и переделан (2026-08-25, решение владельца)**: именованные
«цели» с ссылкой по ключу признаны так себе — каталог стал **статичным хранилищем профилей**
в духе настроек: `Core/Runtime/ChatProfiles.cs` (`[SettingsFile("config/chat-profiles.json")]`,
паттерн AppSettings: `ChatProfiles.Get()` доступен из любого места). Профиль = три
НЕсмешиваемых куска: **SamplerProfile** (семплер+лимиты — то, что уходит в llama.cpp),
**PromptProfile** (промпт+тулы+белый список+усилие мыслей+контракт результата),
**StateBlockProfile** (state-блок ≠ системный промпт; сегодня вкл/выкл). Запись default
гарантирована всегда (файла нет → создаётся; кусок удалён → восстановится) и пуста =
«ровно прежнее поведение» через глобальные настройки. Сессия назначает каждый кусок
СВОИМ ключом (SessionData.SamplerKey/PromptKey/StateBlockKey), null = default. UI:
шестерёнка у панели сессий → диалог назначения кусков; редактирование самих профилей —
во вкладке «Суммаризация». main-агент ведётся идентичностью — промпт/state-куски на него
не действуют (мысль владельца: возможно, отдельный ТИП профиля для main — будущее).
Урок NekoBot учтён дважды: профиль = данные, а не класс; статика = источник правды.

## Будущее: параллельные ходы (TurnRegistry сделан, scope в работе)

Триггер — оркестратор (spawn дочерних агентов). Две вещи были спроектированы заранее;
**TurnRegistry готов (2026-08-25)**, AgentRuntime-scope начат:

**TurnRegistry** — сделан: `Core/Runtime/` (TurnState/TurnEntry/TurnRegistry) — каждый
фоновый ход получает личность: Guid, имя, состояние Queued→Running→терминал, журнал
этапов, токен отмены. Исполнитель — `BackgroundWork` поверх реестра (контракт Queue
не менялся; все сайты переведены автоматически), политика прежняя (OCE штатный путь,
прочие исключения → статус). UI — `TurnPanel` + Expander внизу MainWindow: список
(состояние цветом, имя, длительность, журнал в tooltip, отмена активных) вместо одной
статусной строки. Дочерние ходы оркестратора зарегистрируются здесь же.

**AgentRuntime-scope** — процессная статика (`AgentInteraction`, `SettingsStore<T>`,
`ChatSessions.Root`) переезжает в скоуп-объект агента: свой каталог сессий, свой маршрут
интерактива (окно у main, очередь у дочерних), свой профиль настроек. Миграция
постепенная: новые подсистемы принимают scope-параметр, старые — по касанию.
**Шаг 1 сделан (2026-08-25)**: `Core/Runtime/AgentRuntime.cs` — скоуп с провайдером
настроек и маршрутом интерактива; `AgentLoopRequest.Runtime` и `ToolContext.Runtime`
несут скоуп до цикла и инструментов (null → main); `AgentInteraction` стал фасадом над
`Main`. Цикл читает конфиг из профиля скоупа, ask_user/shell тянут интерактив из
контекста. Осталось: сессии (ChatSessions.Root), скрытые статические чтения настроек
в Core/Memory, маршруты интерактива у дочерних (окно vs очередь).

Потоковая модель при этом пересматривается целиком (см. главный инвариант выше):
файловые сервисы готовы к многопоточности (AtomicFile, устойчивые List), узкие места —
UI-коллекции (маршалинг) и перечисленная статика.

## Осознанные жертвы расширяемости

Полный список с причинами — в refactoring.md («Роль MainViewModel и жертвы…»). Кратко:
генерационный switch в VM (до оркестратора), главный поток как инвариант, процессная
статика (с 2026-08-25 это фасады над `AgentRuntime.Main` — маршрутизация через
`Runtime`-параметры уже возможна), фиксированные сборки тулов (шов Register уже есть).
