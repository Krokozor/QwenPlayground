# Refactoring.md — записная книжка проекта

Рабочие заметки по улучшению QwenPlayground. Точка референса: что найдено, что сделано, куда идти.

## Принципы (заданы владельцем проекта)

- **Расширяемость > микрооптимизации.** Не разменивать гибкость архитектуры на экономию тактов.
- **Класс = файл.** Если класс просит собственный файл или разделение — не лениться.
- **Комментировать несамоочевидное.** Шапка файла или комментарии в функциях. Мысли о развитии проекта сохранять здесь или в коде.

## Архитектура вкратце

- `Core/Agent` — агентный цикл (prompt → stream → parse → tools → повтор).
- `Core/Orchestration` — мультиагентный режим: директор + подчинённые через общий чат.
- `Core/Tools` — рефлексивный реестр инструментов ([Tool]/[ToolParameter]).
- `Core/Inference` — HTTP-клиент к llama.cpp-серверу (нативный `/completion` + `/tokenize`).
- `Core/Templates` — рендер chat-template Qwen и парсер вывода (`<tool_call>`, `<think>`).
- `Core/Roslyn` — анализ собственного солюшена (диагностика, символы, outline).
- `Core/SelfBuild` — самосборка: build → test-gate → restart через Launcher.
- `Core/Heartbeat` — wake-сигналы: файловая очередь `wake/*.txt`, внешний способ разбудить агента без UI.
- `Core/MetaInfo` — state-блок `<state>…</state>`: снапшот статуса на момент генерации (msg_id, время, context cur/max, сборка, nag), префиллится в начало think при каждом рендере, персистится в `message.StateBlock`, шаблон рендерит его у каждого прошлого хода — модель видит, как статус МЕНЯЕТСЯ. Парсер вырезает блок из мышления модели (не попадает в историю как мысли).
- `Core/Memory` — память L1/L2/L3 (`sessions/main/layers.json`): L1 — биография/идентичность, L2 — планы/цели, L3 — эпизоды ходов; инжектится в системный промпт при каждой сборке, НЕ в history. Долговременные факты — `memories/`.
- `App` — WPF UI (MVVM, CommunityToolkit) + main-агент: постоянная сессия `sessions/main/chat.json`, идентичность в `main-agent.md`, heartbeat-таймер, всегда-включённое мышление с reasoning effort (xhigh/medium/low).

### Дизайн: heartbeat / main-агент / мета-блок (2026-08-16)

- **Main-агент** — сессия с id `main` грузится при старте по умолчанию; её нельзя удалить.
  Идентичность (`system`-сообщение первой в истории) читается из `main-agent.md` при каждом
  старте и при каждой загрузке сессии — правится файлом без перекомпиляции (агентом или владельцем).
- **Heartbeat** — `DispatcherTimer` (опрос 20 с) в MainViewModel: wake-сигналы из `wake/`
  обрабатываются вне расписания, плановое пробуждение — раз в `HeartbeatIntervalMinutes`.
  Ходы heartbeat всегда агентные (`forceAgentic`), даже если в UI выбран чат-режим.
  Защита от наложения: `IsGenerating`; контекстный бюджет — общий с обычными ходами.
- **Мета-блок** — `AgentLoop.metaProvider` вызывается перед каждым рендером; блок дописывается
  в `QwenChatTemplate.Render(metaBlock:)` после открывающего think (при выключенном мышлении —
  игнорируется, иначе попал бы в видимый ответ). В историю не попадает: `QwenOutputParser`
  срезает ведущий блок.
### Дизайн: state-блок, always-thinking, память L1-L3, лаунчер (2026-08-17)

- **State-блок вместо мета-блока** — `<state>…</state>`, снапшот системного статуса, вставляется
  в начало think КАЖДОГО assistant-сообщения и префиллится в генерацию. ПЕРСИСТИРУЕТСЯ
  с сообщением (`message.StateBlock`), шаблон рендерит его у прошлых ходов — модель видит
  рост контекста/смену билда между ходами. Парсер вырезает блок из мышления (StateBlock.SplitLeading).
  Единственный владелец блока — `Core/MetaInfo/StateBlock.cs` (Build/WithField/Parse/SplitLeading).
  Nag sanity_check подмешивается как поле `nag` внутрь state-блока.
- **Мышление всегда включено** — `ApplySettings` жёстко ставит `EnableThinking/PreserveThinking = true`
  (правка settings.json не выключит); тумблеры из UI убраны. Reasoning effort — только
  `xhigh`/`medium`/`low` (как в официальной `assets/chat_template.jinja`): `xhigh` = «думать много»,
  `low` = «думать меньше». Управление в ComboBox усилия, пробрасывается в рендер.
- **Память L1/L2/L3** (main-агент, `sessions/main/`): L1 — биография/идентичность (семя — старое
  резюме из system при миграции), L2 — планы/цели, L3 — эпизоды ходов. Конвейер
  (`MemoryLayerPipeline`): 4 изолированных LLM-вызова — merge L1+L2→Temp, валидация→факты,
  сегмент 50% чата→L3, сверка→факты; ротация Temp→L1, L3→L2 механическая. Факты → `memories/`
  (source=compaction). Слои инжектятся в системный промпт при каждой сборке.
  Миграция `sessions/main.json` → `sessions/main/chat.json` однократная (`EnsureMainMigrated`),
  исходник в `backups/`.
- **Лаунчер** — WPF GUI (`tools/QwenPlayground.Launcher`): кнопки «Запустить приложение» /
  «Пересобрать и запустить», headless-путь `pid [buildId]` для self-rebuild. Корень резолвится
  через `SelfBuildPaths.RunRoot` (работает из `run/` и из dev-билда). `SelfBuildService.BuildNextAsync`
  сам пересобирает лаунчер в `run/` при каждой сборке.
- **Опасность саморедакции**: литеральные системные токены шаблона нельзя писать в видимый
  ответ и в аргументы tool_call (парсер чата обрезит сообщение/аргументы). Приёмы: \x-экраны
  в C# (`\x3c`/`\x3e`), python-патчи с маркерными строками (`Sandbox/patch_template_meta.py`,
  `Sandbox/patch_agentloop_meta.py`), виртуальная разметка `Sandbox/compile.py`/`decompile.py`.

### 2026-09-04 — код-аудит: заглушки, хардкод, сомнительные места

Свип всего `src/` (413 .cs) на заглушки/захардкоженные значения/сомнительные места. В целом код чистый:
нет TODO/FIXME (кроме одного осознанного), нет NotImplemented, пустых catch без комментариев и
захардкоженных адресов/ключей. Найдено:

**Живые баги**
1. **`grep` include-фильтр** (`Tools/Builtins/ProjectFiles.cs`) — паттерн `*.cs` передаётся в
   `Matcher.AddInclude` как есть; в FileSystemGlobbing паттерн без `**` матчит только корневой
   уровень → `grep include="*.cs"` молча возвращает "no matches". Известная грабель (записана
   2026-09-03, workaround `**/*.cs`), в коде НЕ зафиксирована. Лечение: в `Enumerate` нормализовать —
   если в паттерне нет `/` и `**`, предпоставить `**/`.
2. **`BrowserService.cs:616`** — network log захардкодил `["method"] = "GET"`: все запросы в
   `browser_network` показываются GET. `e.Request?.Method` доступен — взять оттуда.
3. **`MemoryLayerPipeline.RunAsync`** (строки ~96–103) — ветка «L1 пуст, L2 заполнен, L3 пуст»:
   `L2 = hasL3 ? current.L3 : current.L2` кладёт старое L2 и в L1, и в L2 (дубль в системном
   промпте). Обычным каскадом недостижимо, но через ручную правку layers.json — да. Лечение:
   `L2 = hasL3 ? current.L3.Trim() : string.Empty`.

**Несогласованности / сомнительное**
4. `ContextMaintenance.CompactLayersAsync` — факты сохраняются `Take(MemoryExtractor.MaxFacts)`,

5. `QwenChatTemplate.AppendAssistant` (стр. 236) — мутация входа при рендере:

   несколько сообщений — перекрёстное заражение.
6. `ShellTool.DangerousPatterns` — наивные подстроки: `Contains("del ")` ложно срабатывает на
   «model » (`echo model`), а `rd`/`erase`/`del` в конце команды пропускает. Это подсказка для
   подтверждения, а не security-граница — оформить как таковую (или word-boundary).
7. `LlmCompletionClient.CountTokensAsync` — два голых `catch { }` глотают ВСЁ (включая OOM и
   баги в своём коде). Сужить до `HttpRequestException or JsonException or IOException`.
8. **`TokenCounter` — мёртвый код**: нигде не вызывается (BPETokenizer помечен WIP/выведен из
   использования 2026-08-20, но TokenCounter его всё ещё грузит). Удалить или пометить так же.
9. `BPETokenizer.EncodeWord` — неизвестный merge молча добавляет токен ID 0 (BOS) в результат.
   Опасный тихий фолбэк даже для WIP-кода.

### 2026-09-02 (45) — rebuild_self: честный git-статус + пуш по настройке (PushOnRebuild)

неравенстве (т.е. просто при наличии незапушенных коммитов) выводил вводящую в заблуждение
приписку про интернет.

  «Самосборка (rebuild_self)» в настройках. Включён — после успешного билда `git push`
  (только уже закоммиченное; инструмент не коммитит).
- **RebuildSelfTool**: статус теперь честный — «(N unpushed commit(s))» / «(up-to-date with
  origin)» / «(no upstream)»; RunGit возвращает exit code + stderr (git пишет результат в
  stderr), у пуша таймаут 60 с.
- Сборка 20260902-122919 success.

## Роль MainViewModel и жертвы расширяемости (аудит 2026-08-22)

**Что VM делает сейчас** (после трёх шагов сдутия, 1222 строки): экран-модель (INPC-состояние + команды), композиционный корень (сборка ~12 сервисов в ctor, регистрация AgentInteraction), протокол-адаптер цикла (switch по AgentEvent → мутации UI-коллекций — самая ценная часть), владелец разговора (`_conversation` — источник истины контента + счётчик ID), триггер персистентности (SaveCurrent после хода).

**Чем должен быть по принципу**: только (1) состояние экрана + команды, (2) перевод доменного потока событий в видимое, (3) владение контентом разговора как данными экрана. Не должен: быть композиционным корнем (→ сборка в Composition/App-startup, ctor получит готовые сервисы — уйдут 95 строк и циклические связки вида pipelineRef), реализовать окна ask/confirm инлайн (→ отдельный ChatInteraction, регистрирующий AgentInteraction), держать тела heartbeat-хода и flush памяти (→ делегаты уже есть, тела можно отдать сервисам).

**Жертвы расширяемости** (осознанные и нет, по убыванию боли):

1. **`_conversation` — голый List без владельца** (главный налог). Пишут: VM (send/rollback), AgentLoop (assistant/tool/nag), ContextMaintenance (компакция). Читают все. Нет событий изменения и инвариантов — каждый новый писатель обязан «знать» про RebuildMessageViews/AssignPendingIds/SaveCurrent вручную. Лекарство: ChatLog-объект с событиями (следующий большой выигрыш; делать при появлении оркестратора или второго экрана чата).
2. **GenerateCoreAsync-switch** — обработка AgentEvent'ов зашита в VM: новый тип события протокола агент↔UI требует правки switch. Пока один потребитель — терпимо; при оркестраторе → реестр обработчиков/шина.
3. **Главный поток как инвариант** — тяжёлые вычисления в Core будут фризить UI; параллельные ходы (несколько агентов) потребуют пересмотра модели. Фундаментальная плата за простоту (NekoBot-стиль), принята осознанно.
4. **AgentInteraction / SettingsStore&lt;T&gt; / ChatSessions.Root — статика на процесс**: второй набор провайдеров/настроек/каталога сессий невозможен; тесты делят глобальное состояние (параллельность ограничена). Плата за pull-модель без DI-контейнера; при необходимости — скоуп-объекты.
5. **Rollback: параллельная мутация Messages/_conversation по индексу** — инвариант 1:1 не enforced, новый тип view сломает тихо. Лечится тем же ChatLog.
6. **ToolRegistry сканирует две фиксированные сборки** (`typeof(AgentTool).Assembly, typeof(MainViewModel).Assembly`) — плагинные инструменты (MCP, см. backlog) потребуют точки регистрации. Мелочь, станет актуальной вместе с MCP-клиентом.
