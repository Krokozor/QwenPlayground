# Ключевые концепции

Это руководство объясняет, как устроен QwenPlayground изнутри. Если вы новый разработчик или хотите понять, как работает агент, начните отсюда.

## Агентный цикл

Агентный цикл — это сердце QwenPlayground. Вот что происходит при каждом ходе:

```
Пользователь отправляет сообщение
  ↓
Сборка промпта:
  - история чата (последние N сообщений)
  - системный промпт (идентичность + слои памяти + trajectory)
  - определения инструментов
  - state-блок (служебная информация)
  ↓
Модель генерирует ответ (стриминг)
  ↓
Парсинг ответа:
  - если есть tool_call → выполнить инструмент, добавить результат в историю, повторить цикл
  - если нет tool_call → завершить ход
  ↓
Сохранение сессии
```

Цикл продолжается до:
- завершения задачи (модель не вызывает больше инструментов)
- исчерпания лимита итераций (`MaxIterations`, по умолчанию 50)
- отмены пользователем

**Важно:** весь агентный код исполняется на UI-потоке. Это осознанный инвариант проекта — он упрощает работу с состоянием (не нужны блокировки), но тяжёлые вычисления должны уходить в `Task.Run`.

## State-блок

State-блок — это служебная информация, которая вставляется в начало каждого хода модели. Он выглядит так:

```
<state>
msg_id=6360
time=2026-09-03 23:52:49
context=5328/204800
build=20260903-224006:success
mem=359673e16ce340c18a9d1e16b36a132e | relevance ~1.00 | Open-source audit round 3...
pair=c02281b3a7454f24ae67e6dd5971a847 ~ 83307bffdc604bb69dade2bf550f6923
</state>
```

Поля:
- **msg_id** — стабильный ID текущего сообщения (монотонный счётчик сессии)
- **time** — текущее время
- **context** — использовано/максимум токенов в контексте
- **build** — ID последней сборки и её статус
- **mem** — воспоминания, которые модель сочла релевантными (из ассоциативной памяти)
- **pair** — пары фактов, которые могут быть дубликатами (требуют решения через `memory_manage`)
- **nag** — напоминание о самопроверке (если ход слишком длинный)

State-блок перистируется с сообщением — по истории чата видно, как менялось состояние приложения.

**Для модели:** state-блок — это не её мысли, а служебная информация приложения. Модель не должна повторять его или редактировать. Мысль продолжается после `</state>`.

## Память

QwenPlayground использует три типа памяти:

### 1. Ассоциативная память (`memories/`)

Долговременные факты, которые модель запоминает во время работы. Каждый факт — отдельный JSON-файл в `memories/`.

**Как работает:**
- Модель может сохранять факты через инструмент `memory_add`
- После каждого хода и между итерациями агент делает "реколл" — ищет релевантные факты
- Релевантные факты всплывают в state-блок (строки `mem=...`)
- Периодически агент получает "наг" — напоминание проверить память на дубликаты

**Структура:**
```
memories/
├── index.md          # Список всех фактов (id, категория, эмодзи, заголовок)
├── 359673e16ce340c18a9d1e16b36a132e.json  # Факт (content, category, emoji, date)
├── 83307bffdc604bb69dade2bf550f6923.json
└── ...
```

**Классификация:** факты могут иметь категорию и эмодзи (например, "🔧 фикс бага", "💡 идея"). Классификация делается лениво — через "компаньон-модель" (опционально) или по тексту.

### 2. Слои памяти (L1/L2/L3)

Дистиллированное резюме истории чата. Лежат в `sessions/<id>/layers.json`.

- **L3** — самый свежий слой: при компакции в него сжимается примерно половина чата
- **L2** — средний слой: становится из старого L3
- **L1** — самый старый дистиллят: слияние старого L1 и L2

**Как работает:**
1. Контекст приближается к лимиту → запускается компакция
2. Ранние сообщения сжимаются в новый L3
3. Старый L3 становится L2, старый L1 + L2 сливаются в новый L1
4. Факты из сжатых сообщений извлекаются в `memories/`

**Для чего:** слои переживают рестарты и компакции. Модель всегда видит дистиллированную историю в системном промпте, даже если конкретные сообщения уже вытеснены из контекста.

### 3. Дневник (`diary.md`)

Человекочитаемая история. Записывается при компакции — краткое описание того, что произошло.

**Для чего:** владелец может посмотреть, что агент делал, даже если не читает весь чат.

## Компакция

Компакция — автоматическое сжатие контекста, когда он приближается к лимиту.

**Как работает:**
1. Перед каждой генерацией проверяется бюджет: `/tokenize` следующего промпта vs окно − резерв
2. Если не влезает → запускается компакция
3. Бэкап сессии (без него не сжимаем)
4. Ранние сообщения сжимаются в слои (L1/L2/L3)
5. Факты извлекаются в `memories/`
6. Контекст уменьшается, цикл продолжается

**Параметры:**
- `ContextSize` — размер контекста (по умолчанию 32768)
- `CompactKeepRatio` — доля недавних сообщений, которые сохраняются дословно (по умолчанию 0.5)

**Для пользователя:** компакция происходит автоматически, вы не видите её напрямую. Но можете посмотреть вкладку «Суммаризация», чтобы увидеть слои и управлять ими вручную.

## Heartbeat

Heartbeat — периодические пробуждения агента.

**Как работает:**
- По умолчанию каждые 30 минут (настраивается через `HeartbeatIntervalMinutes`)
- Агент получает "heartbeat-ход" — как если бы пользователь отправил пустое сообщение
- Агент может выполнять фоновые задачи:
  - проверять `refactoring.md` на незакрытые пункты
  - делать самопроверку (sanity check)
  - обновлять память (классификация, дедупликация)
  - если делать нечего — коротко сообщить статус и остановиться

**Wake-сигналы:** можно разбудить агента вне расписания, положив файл в `wake/`:
```bash
echo "Проверь, всё ли работает" > wake/check.txt
```
Агент обработает его при следующем heartbeat-тике (опрос каждые 20 секунд).

## Самосборка (rebuild_self)

Агент может править собственный код и пересобирать приложение.

**Как работает:**
1. Агент правит код (через `edit_file`, `write_file`)
2. Вызывает `rebuild_self`
3. Приложение:
   - запускает `dotnet build` (с Roslyn-гейтом: проверка ошибок без полной сборки)
   - запускает тесты
   - копирует сборку в `run/<id>/`
   - обновляет `run/current.txt` (указатель на активную версию)
   - рестартует себя через handshake с лаунчером

**Безопасность:**
- По умолчанию `rebuild_self` не пушит в git (только если включено `PushOnRebuild`)
- Каталог `run/` не трогать руками — только через `rebuild_self`
- Если сборка падает — агент видит ошибки и может их исправить

## Инструменты

Агент имеет доступ к набору инструментов. Основные:

**Файловые:**
- `read_file` — прочитать файл
- `write_file` — записать файл
- `edit_file` — точечная правка (заменить old_string на new_string)
- `glob` — найти файлы по паттерну
- `grep` — поиск по содержимому
- `shell` — выполнить shell-команду

**Roslyn (анализ C#):**
- `csharp_diagnostics` — ошибки компиляции без сборки
- `csharp_symbol` — найти определение символа
- `csharp_references` — все ссылки на символ
- `csharp_callers` — кто вызывает метод
- `csharp_outline` — структура файла/пространства имён
- `csharp_class_map` — иерархия типов

**Приложение:**
- `screenshot` — скриншот окна приложения
- `switch_tab` — переключить вкладку
- `app_window` — максимизировать/восстановить окно
- `sanity_check` — самопроверка в длинных ходах

**Память:**
- `memory_add` — сохранить факт
- `memory_list` — список фактов
- `memory_get` — прочитать факт
- `memory_manage` — управление памятью (дедупликация, merge)

**Браузер (WebView2):**
- `browser_navigate` — открыть URL
- `browser_click` — кликнуть
- `browser_type` — ввести текст
- `browser_screenshot` — скриншот страницы
- `browser_evaluate` — выполнить JS
- (и другие: hover, scroll, select, wait, extract, console)

**Shelf-система:** инструменты сгруппированы по доменам. Core-инструменты всегда доступны, Browser и CSharp — по требованию (через `activate_shelf`/`deactivate_shelf`). Это экономит токены: неактивные инструменты не попадают в промпт.

## Мультимодальность

Агент может видеть изображения:

- **Скриншоты** — через `screenshot` (окно приложения) или `browser_screenshot` (веб-страница)
- **Изображения** — через `load_image` (агент видит картинку в следующем рендере)
- **Вложения** — пользователь может прикрепить файл к сообщению (иконка 📎)

**Как работает:**
1. Изображение копируется в `sessions/<id>/artifacts/msg_<msgId>/`
2. При рендере промпта вставляется маркер (специальный токен)
3. Base64 изображения отправляется в LLM-сервер через `multimodal_data`
4. Модель видит картинку и может описать её

**Очистка:** чтобы не жечь контекст, агент может вызвать `remove_attachments` — изображение убирается из контекста (но остаётся на диске).

## Настройки

Все настройки живут в `settings.json`. Источник правды — типизированный синглтон `AppSettings.Get()`.

**Основные параметры:**
- `Endpoint` — адрес LLM-сервера
- `MaxTokens` — максимальная длина ответа
- `ContextSize` — размер контекста
- `ReasoningEffort` — усилие размышления (XHigh/Medium/Low)
- `Temperature/TopP/TopK/MinP` — параметры семплирования
- `MaxIterations` — лимит итераций агентного цикла (0 = без лимита)
- `HeartbeatEnabled/HeartbeatIntervalMinutes` — heartbeat
- `MemoryEnabled` — мастер-переключатель памяти
- `CompanionEndpoint/CompanionEnabled` — компаньон-модель (опционально)

**Как читать настройки:** в коде всегда через `AppSettings.Get().SomeProperty`, а не через параметры сигнатур. Это паттерн NekoBot — настройки читаются в точке использования.

## Сессии

Каждая сессия — это отдельный разговор с агентом. Лежат в `sessions/`:

```
sessions/
├── main/              # Main-агент (нельзя удалить)
│   ├── chat.json      # История чата
│   ├── layers.json    # Слои L1/L2/L3
│   └── artifacts/     # Вложения (изображения)
├── index.json         # Индекс сессий (id, title, updatedAt)
└── <session-id>/      # Другие сессии
    ├── chat.json
    ├── layers.json
    └── artifacts/
```

**Main-агент** — особая сессия, которая загружается при старте. Её идентичность читается из `main-agent.md`, trajectory — из `trajectory.md`.

**Другие сессии** — обычные чаты. Можно создавать, переключаться, удалять.

## Proфили чата (ChatProfiles)

Каждая сессия может иметь свой профиль: параметры семплирования, промпт, инструменты, усилие размышления.

**Структура:**
- `SamplerProfile` — параметры семплирования (temperature, top_p, max_tokens, seed)
- `PromptProfile` — системный промпт, инструменты, белый список, усилие размышления
- `StateBlockProfile` — включить/выключить state-блок

**Хранение:** `config/chat-profiles.json` (по паттерн AppSettings). Запись `default` гарантирована — если файла нет, создаётся пустой (поведение = глобальные настройки).

**Назначение:** шестерёнка у панели сессий → диалог назначения профилей. Редактирование самих профилей — во вкладке «Настройки».

## TurnRegistry

У каждого фонового хода есть "личность": Guid, имя, состояние (Queued→Running→терминал), журнал этапов, токен отмены.

**Для чего:** оркестратор (будущая фича) сможет запускать дочерних агентов параллельно. Каждый ход будет зарегистрирован в TurnRegistry, и UI покажет список активных ходов.

**UI:** панель внизу главного окна (Expander) — список ходов с состоянием, длительностью, журналом в tooltip, кнопкой отмены.
